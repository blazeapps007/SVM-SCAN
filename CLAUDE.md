## Commands

pnpm workspace monorepo — run commands from the repo root, they fan out via `pnpm -r`:

- **Lint**: `pnpm lint` · **Type check**: `pnpm check` · **Test**: `pnpm test` · **Build**: `pnpm build`
- **Dev servers**: `pnpm dev:web` (Vite, http://localhost:5173) / `pnpm dev:api` (Fastify, http://localhost:4000, auto-restarts via `tsx watch`)
- Target a single workspace: `pnpm --filter @dexplorer/web <script>` / `pnpm --filter @dexplorer/api <script>` / `pnpm --filter @dexplorer/shared <script>`
- Single test file: `pnpm --filter @dexplorer/web test src/utils/helper.test.ts`
- `apps/api`'s `build`/`check` scripts are both just `tsc -b --noEmit` — there is no compile/bundle step; `tsx` runs TypeScript directly at dev/runtime.

CI (`.github/workflows/ci.yml`) runs install → `pnpm -r lint/check/test/build` on every push/PR to `main` — this is the only enforcement point; there is no local pre-commit hook (Husky + lint-staged were removed after repeatedly breaking commits from GUI git clients on Windows). Run `pnpm lint`/`pnpm check` yourself before committing.

## Project Overview

SVM Scan is a block explorer for the **Steem Virtual Machine** chain — a Cosmos SDK chain with an EVM execution layer and a custom cross-chain bridge module bolted on. It's a fork of [arifintahu/dexplorer](https://github.com/arifintahu/dexplorer) (a frontend-only Cosmos explorer, hence the `@dexplorer/*` package names) that has since diverged substantially: a persistent indexed backend, MongoDB storage, EVM support, and the Steem bridge/name-service features below. Three workspaces:

- **`apps/api`** (`@dexplorer/api`) — a Fastify + MongoDB backend that indexes the Cosmos side of the chain from genesis: a resumable backfill walks block-by-block via Tendermint RPC, then a live subscription tails new blocks. Validators/params/proposals/bridge data are refreshed on a timer (low-churn, not per-block). Serves everything over a REST API.
- **`apps/web`** (`@dexplorer/web`) — the React/Vite frontend. It has **no direct chain connection** — it only talks to `apps/api` over HTTP/REST via TanStack Query. The backend indexes one chain, configured via its own `RPC_ADDRESS` env var.
- **`packages/shared`** (`@dexplorer/shared`) — code that must be identical on both sides: `decodeMsg`/`DecodeMsg` (the Cosmos SDK message-type registry, see below), denom-conversion utils, proposal-status labels, and the REST API's TypeScript response contracts (`src/types/api.ts`).

Data survives reloads (it's in MongoDB, not browser memory) and history goes back further than the last N in-memory blocks — this is the whole reason the backend exists; the original frontend-only fork held only a rolling window of recent blocks/txs in Redux.

### Tech Stack

- **apps/web**: React 18, TypeScript, Vite, Tailwind CSS, TanStack Query (all data fetching), React Router. No Redux/Zustand — removed once the RPC/streaming code they supported was deleted.
- **apps/api**: Fastify, native `mongodb` driver + Zod schemas (not Mongoose — matches the workspace's strict no-`any` policy), `@cosmjs/tendermint-rpc`/`@cosmjs/stargate` for Cosmos-side chain queries, raw `fetch`-based JSON-RPC calls for the EVM side (`chain/evmRpc.ts`) and a custom LCD/REST client for the bridge module (`chain/steembridgeLcd.ts`), `xstream` for the live block subscription, `tsx` for dev/run (no compile step).
- Both: i18next-free on the API side; frontend keeps Framer Motion, Sonner, i18next.

## Architecture

### `apps/api` — indexer + REST API

- `src/chain/` — `client.ts` (connect/validate a websocket `Tendermint37Client`, with failover across `RPC_ADDRESS`/`RPC_ADDRESS_BACKUP_1`/`RPC_ADDRESS_BACKUP_2` tried in order on (re)connect), `abci.ts` (raw ABCI queries against staking/mint/gov/distribution/slashing modules), `query.ts` (`getBlock`/`getBlockResults`/`getNetworkStatus`/account & balance lookups), `subscribe.ts` (live block/tx subscriptions), `withTimeout.ts` (wraps any chain/HTTP call so a dropped connection fails fast instead of hanging forever — plain `fetch()` has no default timeout in Node), `evmRpc.ts` (raw EVM JSON-RPC: tx/receipt fetch, ERC-20 metadata, token-transfer log decoding, Uniswap V3-style `PoolCreated` log decoding), `steembridgeLcd.ts` (typed client for the chain's custom `steembridge` module over LCD/REST — no generated proto exists for it, see below), `helpers.ts` (`bech32ToEvmAddress` and similar cross-encoding helpers), `connectionHealth.ts`.
- `src/indexer/run.ts` is the orchestrator, split into two phases so the API can start serving before history catches up: `connectIndexer()` (fast path — connect with failover, `ensureIndexes()`, get-or-create the `indexerState` doc — enough for the server to accept requests) and `runIndexer()` (slow path, not awaited by the caller — initial refreshers for params/denom metadata/validators/proposals/bridge deposits/bridge withdrawals, then `backfillRange()` from `indexerState.lastIndexedHeight+1` to head, then flip to live tail (`liveTail.ts`, gap-detection falls back to backfill), then `setInterval` refreshers for validators/params/proposals/bridge deposits/bridge withdrawals). `checkpoint.ts` persists progress to the `indexerState` singleton doc after every batch, so a restart resumes instead of re-indexing from 0 — this is load-bearing, don't remove the checkpoint write from the batch loop.
- `src/indexer/proposalRefresh.ts` queries proposals via ABCI (`chain/abci.ts`'s `queryProposals`, `cosmjs-types`-decoded) but that path comes back with `submitTime`/`depositEndTime`/`votingStartTime`/`votingEndTime` all `undefined` on this chain — root cause unconfirmed, the chain demonstrably has real values for all four (verified live via LCD). `chain/govLcd.ts`'s `fetchProposalExtra()` (standard Cosmos SDK gov v1 LCD REST, not steembridge-specific but on the same `STEEMBRIDGE_LCD_URL`) backfills those four fields plus `expedited`/`failedReason` when the LCD is configured; without it, those fields stay null/false/empty exactly like before this existed. If a proposal's dates are inexplicably null despite the chain clearly having them, check this LCD gap before assuming the ABCI query itself is broken end-to-end — everything else on `Proposal` (status, tally, messages, proposer, totalDeposit) decodes fine via ABCI, it's specifically these `google.protobuf.Timestamp` fields (and the two v1 fields LCD-only) that don't.
- `src/indexer/blockIndexer.ts` is the core per-height unit: fetches block + `blockResults`, decodes every tx (`Tx.decode` + `decodeMsg` per message from `@dexplorer/shared`), extracts `senders` (`getSendersFromEvents`) and `ibcTransfer` (`indexer/ibcTransfer.ts`, scans IBC packet events) at index time, calls `indexLiquidityPoolsForTx()` (enrichment, best-effort — failures there must not break block indexing) for any `MsgEthereumTx` message, and upserts — both backfill and live-tail call this same function so the two paths can't produce divergent doc shapes. The tx doc's `fee` is the decoded `auth_info.fee` *unless* that's empty, in which case it falls back to `indexLiquidityPoolsForTx()`'s computed EVM fee (see below) — a `MsgEthereumTx` always has an empty `auth_info.fee` on this chain, so without this fallback every EVM tx would show no fee anywhere a tx doc's `fee` field is read (Transactions list, Transaction Detail's headline Fee row).
- `src/indexer/liquidityPools.ts` — for every `/cosmos.evm.vm.v1.MsgEthereumTx` in an indexed tx, fetches the EVM receipt once and uses it for two things: (1) checking its logs for a Uniswap V3-style `PoolCreated` event, upserting a `liquidityPools` doc on a match (token pair + metadata, fee tier, tick spacing), and (2) computing `gasUsed * effectiveGasPrice` as the tx's real native (`asteem`) fee, returned to `blockIndexer.ts` as `EvmTxEnrichment.fee` — the EVM ante handler deducts gas cost directly rather than through the standard Cosmos fee field, so `auth_info.fee` is always empty for these txs and this is the only place the real cost is observable. Both only run when `EVM_RPC_URL` is set. `routes/evm.ts`'s `/evm/tx/:hash` computes the same `gasUsed * effectiveGasPrice` fee independently (as `EvmTransactionDetails.fee`/`gasPrice`) for the live, per-request EVM-only path (`TransactionDetail.tsx`'s `EvmExecutionPanel`, used both inline for an indexed wrapper tx and standalone when no wrapper is indexed yet) — this duplication is deliberate, not a shared helper, since one runs at index time against an already-fetched receipt and the other runs live against a fresh one.
- `src/indexer/bridgeDepositRefresh.ts` / `bridgeWithdrawalRefresh.ts` — poll the `steembridge` LCD module (Steem/SBD deposit oracle attestations and withdrawal requests) on a timer and upsert into their own collections. Only run when `STEEMBRIDGE_LCD_URL` is set. Unlike the Cosmos-side data, this is *not* block-by-block indexing — the module has list-all query endpoints, so it's periodic polling instead.
- `src/indexer/paramsRefresh.ts` also refreshes `steembridge`/`oracledata` module *params* (governance config — bridge enable flags/thresholds/fees/timeouts, oracle vote period/threshold/reward-miss bands/whitelist) into the same `chainParams` collection as the ABCI-sourced ones, under keys `'bridge'`/`'oracle'`, gated on `STEEMBRIDGE_LCD_URL`. Since these come from LCD/REST JSON (`chain/steembridgeLcd.ts`'s `fetchBridgeParams`, `chain/oracleLcd.ts`'s `fetchOracleParams`) rather than ABCI/protobuf, their raw fields are snake_case `sdk.Dec` strings already in human decimal form (e.g. `"0.500000000000000000"`) — mapped to the camelCase `BridgeParams`/`OracleParams` shared types at refresh time, *not* the raw-scaled-bytes encoding the ABCI-sourced modules use (see `Parameters.tsx`'s `formatDecPercent` vs `formatRate` on the frontend for the display-side consequence of that distinction).
- The ABCI-sourced params (`staking`/`mint`/`distribution`/`slashing`/`govVoting`/`govDeposit`/`govTally`) used to be stored completely raw — `(await queryXParams(tmClient)).params` straight into Mongo, no mapping, unlike bridge/oracle above. This shipped a real bug: cosmjs-types decodes several of these fields as native `bigint` (`mint.blocksPerYear`, `slashing.signedBlocksWindow`, any `Duration.seconds` — `staking.unbondingTime`, `slashing.downtimeJailDuration`, `gov.votingParams.votingPeriod`, `gov.depositParams.maxDepositPeriod`) or raw `Uint8Array` (`slashing.minSignedPerWindow`/`slashFractionDoubleSign`/`slashFractionDowntime` — cosmjs-types types these as bytes for this module specifically, unlike the equivalent Dec fields elsewhere which are typed `string`). Neither survives a Mongo/JSON round-trip as the plain string the frontend expects, so the values arrived corrupted and rendered as literal `"NaN"` on the Parameters page — not because the data is genuinely unavailable on-chain (confirmed live via LCD: e.g. slashing's `signed_blocks_window`/`min_signed_per_window`/etc. all have real values). `paramsRefresh.ts` now maps each of these fields to a plain string at refresh time (`.toString()` for bigint, a `toDurationShape()` helper for Duration, `decodeDecBytes()` — a byte→ASCII decode, not a rescale — for the Uint8Array Dec fields) before storage. Importantly, `decodeDecBytes()`'s output is still the *raw-scaled* digit string (LegacyDec's `Marshal()` convention, e.g. `"500000000000000000"` for 0.5), not a human `"0.5"` — that's a *different* serialization (`MarshalJSON`, what LCD/REST returns) of the same value, so the frontend's existing `convertRateToPercent` (raw-digit convention) is still the right formatter for these three fields, not `formatDecPercent` (LCD-JSON convention). `distribution` and `govTally` params were already all plain strings and needed no change.
- `routes/params.ts`'s `GET /params/tokenomics` powers the Parameters page's "Tokenomics" section — a chain-wide, mostly-lifetime economics summary distinct from the module *params* `GET /params` already serves. Most of its fields are lifetime aggregates over already-indexed collections (no new indexing work): `totalTxFees` (`$unwind`/`$group`/`$toDecimal` over every tx's `fee`), `totalRewardsDistributed` (the same shape aggregation over `rewardClaims`' `amount`, but *without* the per-validator filter `routes/validators.ts`'s `totalRewardsClaimed` uses — i.e. everyone's claims combined), and `totalBridgeFees` (sum of `bridgeWithdrawals.feeMillisteem`, the protocol fee withheld on every bridge-out). The other two are live, not cumulative: `totalStaked` sums `tokens` across currently-`BOND_STATUS_BONDED` validator docs (a snapshot, not lifetime), and `communityPool` is a live ABCI call (`chain/abci.ts`'s new `queryCommunityPool`, `cosmos.distribution.v1beta1.Query/CommunityPool` — its `DecCoin` amounts need `decodeLegacyDecString` same as any other ABCI Dec field) that's `null` on failure rather than throwing. The whole response is cached 60s (`TtlCache`) since the aggregations are full-collection scans that add up.
- **`totalBurned` is not just bridge-withdrawal principal — ordinary transaction fees are partially burned too**, confirmed by reading the chain's own source (`blazeapps007/SteemVirtualMachine-EVM`, branch `feat/v0.0.3-bridge-oracle` — the code this chain actually runs; `main` doesn't have the bridge/oracle module yet). `x/oracle/bridge/keeper/feesplit.go`'s `SplitFees` runs every `BeginBlock` and splits the *entire* `fee_collector` balance 25%/25%/~50%: 25% to the community pool, 25% to `STEEMBLACKHOLE` (to be burned), and the remaining ~50% (plus rounding remainder) stays in `fee_collector` for normal staker distribution — it also sweeps `bridge_reward`'s balance into `fee_collector` first so the bridge-out fee (`§totalBridgeFees` above) reaches stakers at 100%, assuming `distribution`'s `community_tax = 0`. `x/oracle/bridge/keeper/blackhole.go`'s `SweepBlackHole`, called every `EndBlock`, then burns `STEEMBLACKHOLE`'s *entire* accumulated balance in one `BurnCoins` call — per its own doc comment this is "the app's SOLE burn point," meaning bridge-out net amounts (already known) and this 25% fee-split cut (newly confirmed) are destroyed together, indistinguishable once they land in that module account. Generic cosmos/evm docs claim the EIP-1559 base fee is *not* burned on Cosmos EVM chains by default (distributed to stakers instead) — true for the base-fee mechanism itself, but irrelevant here since this chain layers its own burn on top via the fee-split, independent of EVM's base fee. (Separately, and not the source of this burn: this chain's EVM base fee has decayed to 0 wei — confirmed live via `eth_getBlockByNumber` at several heights — so no EVM transaction has ever actually paid a nonzero gas price here; that's a dead end for gas-price-driven fees specifically, but doesn't matter now that the real mechanism is `fee_collector`-wide, covering Cosmos-side fees too.)
- `indexer/burnEvents.ts`'s `extractBurnedCoins()` reads a block's non-tx events for the standard Cosmos SDK bank module's `"burn"` event (emitted once by `SweepBlackHole`'s `BurnCoins` call) and sums its `amount` attribute by denom — stored as `BlockDoc.burned` (`db/schemas/block.schema.ts`), set in `indexer/blockIndexer.ts` alongside the rest of a block's per-height indexing. Deliberately *not* filtered by burner address: since `STEEMBLACKHOLE` is this chain's sole burn point, any `"burn"` event on the whole chain is necessarily from it, so no dependency on `STEEMBRIDGE_LCD_URL`/`chain/moduleAccounts.ts` is needed just to identify it. `routes/params.ts`'s `getTotalBurned()` now aggregates this field across `blocks` (same `sumCoinArrayField` pipeline shape as `totalTxFees`/`totalRewardsDistributed`) instead of `bridgeWithdrawals` — a strict superset of the old figure, and denominated by real `denom` (`Coin[]`) rather than the bridge `asset` enum (`BridgeAssetTotal[]`), since a fee-split burn has no bridge asset to key off of. **This field is optional and backfill-dependent**: blocks indexed before `burned` existed have no such field and are silently skipped by the aggregation's `$unwind`, so `totalBurned` undercounts until every historical block is re-indexed (the indexer's block upsert is idempotent by height, so replaying `indexBlock()` over old heights — e.g. by resetting `indexerState.lastIndexedHeight` — safely backfills it; there's no separate migration script for this).
- **Landmine already hit once, ship #2**: the first version of `extractBurnedCoins()` read `blockResults.beginBlockEvents`/`endBlockEvents` (the parsed fields `@cosmjs/tendermint-rpc`'s `Tendermint37Client` exposes) and shipped `totalBurned: []` on a full DB wipe + re-index — always empty, never erroring. Root cause: this chain runs CometBFT 0.38 (ABCI 2.0's `FinalizeBlock`, confirmed by the SDK modules' use of `cosmossdk.io/core/appmodule`'s `HasBeginBlocker`/`HasEndBlocker`), whose real `block_results` RPC response has no `begin_block_events`/`end_block_events` fields at all (verified live: the raw JSON's top-level keys are `height, txs_results, finalize_block_events, validator_updates, consensus_param_updates, app_hash` — no begin/end split). `@cosmjs/tendermint-rpc`'s tendermint37 adaptor decodes those two fields as `data.begin_block_events || []` / `data.end_block_events || []` (see its `responses.js`), so on a response with neither key they silently default to `[]` — no error, no signal anything's missing, same "wrong-but-plausible, fails silently" shape as the `typeUrl` landmine documented under "Extending message-type decoding" above. The events (including the `burn` event, confirmed live: `type: "burn", attributes: [{key: "burner", value: "steem10a2y3nc..."}, {key: "amount", value: "15718286073946528asteem"}]`) are all there, just under `finalize_block_events` instead — a comet38-aware client (`Comet38Client`) would parse this correctly via its own `finalizeBlockEvents` field, but this codebase connects with `Tendermint37Client` throughout (`chain/client.ts`), and switching that is a much bigger change than this fix warranted. Fixed with a narrow, best-effort raw JSON-RPC call instead: `chain/query.ts`'s `getFinalizeBlockEvents()` POSTs `block_results` directly to `RPC_ADDRESS` (same "no failover, returns `[]` on any failure" pattern as `getNetworkStatus`'s `net_info` call in the same file) and reads `finalize_block_events` itself. `blockIndexer.ts` merges all three sources (`beginBlockEvents`, `endBlockEvents`, this raw call) into one array before calling `extractBurnedCoins()` — harmless since only one side is ever actually populated for a given node version, and forward-compatible if `@cosmjs/tendermint-rpc` ever adds real comet38 support here.
- The `burn` event isn't purely a "tx fee" signal — it fires **every block, including empty ones**, because `feesplit.go`'s `SplitFees` splits `fee_collector`'s entire balance 25/25/50, and on this chain `fee_collector`'s balance is dominated by `mint`'s per-block inflation reward (routed to `fee_collector` every `BeginBlock` as part of normal Cosmos SDK distribution flow), not by discretionary transaction fees — confirmed live: a single block's mint was `62873144295786114asteem` (~0.063 STEEM) versus this chain's entire lifetime `totalTxFees` of `12363912000000000asteem` (~0.012 STEEM) at the same point in time. So "25% of tx fees are burned" is technically true but understates it: in practice this chain permanently burns roughly 25% of its own block-reward inflation every single block, with actual tx-fee volume a rounding error by comparison — `totalBurned` should be read as "burned via the fee-split + bridge-out mechanism," not narrowly as "burned tx fees."
- `src/routes/*.ts` — one file per resource, registered under `/api` in `server.ts`. Most resources follow the pre-indexed pattern (route reads MongoDB); the deliberate exceptions, which proxy the chain/an external service live with a short in-memory TTL cache (`utils/ttlCache.ts`) instead of indexing: `GET /api/accounts/:address` (balances/sequence are live current-state — indexing balances for every address ever seen is out of scope), `routes/evm.ts` (`/evm/tx/:hash` decodes an EVM transaction on demand from `EVM_RPC_URL`; `/evm/address/:address/tokens` proxies a Blockscout-compatible instance at `EVM_EXPLORER_API_URL` since there's no JSON-RPC call that answers "what tokens does this address hold" — fails soft to `[]`, not an error, since it's supplementary), `routes/nameService.ts` (proxies `steembridgeLcd.ts` live — the LCD has no "list all names" query to walk, unlike deposits/withdrawals, so there's nothing to index), `routes/oracle.ts` (`/oracle/exchange-rates` proxies `chain/oracleLcd.ts`'s `fetchExchangeRates` live, 30s TTL cache — current price data changes every oracle vote period, so there's nothing meaningful to index either), and `routes/proposals.ts`'s `GET /proposals/:id/votes` (proxies `chain/govLcd.ts`'s `fetchProposalVotes` live, no cache — the gov module only retains *individual* vote records while a proposal is still in its deposit/voting period, pruning them once it concludes, unlike the aggregate `finalTallyResult` which `proposalRefresh.ts` indexes separately and which survives conclusion; an empty page for a concluded proposal means "no longer available," not "nobody voted," and the frontend's `ProposalVotesList.tsx` words its empty-state message accordingly based on `proposal.status`).
- `routes/proposals.ts`'s `GET /proposals/:id/votes` resolves each vote's `voter` (a plain account address) to a validator moniker when it is one — re-prefixed to valoper form via `chain/helpers.ts`'s `accountToValoperAddress()` and batch-looked-up with `db/validatorLookup.ts`'s `resolveValidatorMonikers()`, the same re-prefixing trick already used for `MsgAttestDeposit`'s "validator" field. `moniker` is `null` (not omitted) for an ordinary non-validator delegator address; `ProposalVotesList.tsx` links to `/validators/:moniker` when present and falls back to a trimmed `/accounts/:address` link otherwise.

`GET /validators/:identity/attestations` and `.../oracle-submissions` are validator sub-routes reusing already-indexed data: attestations reuses `bridgeDeposits`/`bridgeWithdrawals`' existing `validatorConfirmations` array (matching on `validatorAddress`, merging both collections, sorting by each doc's own confirmation timestamp — not deposit/withdrawal creation time); oracle-submissions queries the already-indexed `transactions` collection for `MsgAggregateExchangeRateVote`/`Prevote` txs sent from this validator's *account*-form address (`chain/helpers.ts`'s `valoperToAccountAddress()`, the reverse of `accountToValoperAddress()`) — neither needed new indexing infrastructure, just new queries over data already being indexed for other reasons. (A third sub-route, `/validators/:identity/blocks` — a "last 100 blocks signed/missed" view backed by a `signedValcons` field on `blocks` — was built, then removed at the user's request; if reintroduced, note that a block's own `lastCommit` attests to the *previous* height, not itself, so it can't be computed in a single pass over that block alone.)

**Landmine already hit once**: a validator's consensus address exists in two encodings — `chain/helpers.ts`'s `pubkeyToValconsAddress()` returns the *bech32* valcons form (needed for the ABCI `querySigningInfo` call in `resolveUptime`), while a block header's `proposer_address` (and any `lastCommit` signature) is *hex*, the same raw bytes with no bech32 encoding. Comparing across the two silently matches nothing (they never compare equal as strings) — this is exactly how the removed block-signing view first shipped broken (every block read as "missed"). `chain/helpers.ts`'s `pubkeyToConsAddressHex()` (sharing a `consensusPubkeyToAddressBytes()` helper with the bech32 version) produces the hex form instead — `ValidatorDoc.consAddressHex` stores it precomputed at refresh time in `validatorRefresh.ts`. This hex form is what `routes/blocks.ts` needs to resolve a block's `proposerAddress` to a validator moniker — `db/validatorLookup.ts`'s `resolveValidatorMonikersByConsAddress()`, keyed on `consAddressHex` — rather than reusing `resolveValidatorMonikers()` (keyed on bech32 `operatorAddress`). `BlockSummary.proposerMoniker` (and therefore `BlockDetailResponse`'s too) is null when no indexed validator's `consAddressHex` matches, e.g. an unbonded/removed validator; `apps/web`'s Blocks/BlockDetail/Home-recent-blocks all render a real `ValidatorIcon` (Steem avatar) when a moniker resolves, falling back to a plain gradient-initial placeholder otherwise.

`routes/validators.ts`'s `GET /validators/:identity` fetches `pendingRewards`/`accumulatedCommission` live via ABCI (`chain/abci.ts`'s `queryValidatorOutstandingRewards`/`queryValidatorCommission`, `cosmos.distribution.v1beta1`), not indexed — these accrue every block, the same "live current-state" reasoning as `GET /accounts/:address` balances, just with a short 15s `TtlCache` instead of none. Both responses' coin amounts are `DecCoin`s (ABCI/`cosmjs-types` decodes `amount` as the raw LegacyDec wire encoding, no decimal point — see `decodeLegacyDecString`'s doc comment) that are *also* atto-denominated, exactly the `delegatorShares` double-scaling gotcha again; `resolveRewards()` decodes the Dec encoding before returning, leaving the standard atto→STEEM conversion to the frontend like every other atto amount. `accumulatedCommission` is a subset of `pendingRewards` (the validator's own cut), not additional to it. Both are `null` (not `[]`) specifically when the live query failed, vs. `[]` for a genuinely-zero result — the frontend must keep that distinction rather than treating both as "nothing to show."
- `src/indexer/rewardClaims.ts`'s `extractRewardClaims()` scans a tx's decoded messages + raw events for `MsgWithdrawDelegatorReward`/`MsgWithdrawValidatorCommission` claims, upserted into the `rewardClaims` collection (`indexRewardClaimsForTx()`, called per tx from `blockIndexer.ts` for both backfill and live-tail, same best-effort/non-blocking pattern as `indexLiquidityPoolsForTx`). The withdrawn `amount` is never on the message itself — only on the resulting `withdraw_rewards`/`withdraw_commission` event — and neither event carries a full identity: `withdraw_rewards` has `validator` but not the claiming delegator's address, `withdraw_commission` has neither (the validator is implicit — the message signer *is* that validator's account). Both gaps are filled by correlating positionally against this tx's messages of the matching type (Nth event of a type ↔ Nth message of that type, since the SDK executes/emits in lockstep) rather than assuming a 1:1 tx-to-claim mapping — a single tx can legitimately contain several claims (e.g. a "claim from every validator" batch). `routes/validators.ts`'s `GET /validators/:identity` computes `totalRewardsClaimed` (`Coin[]`, always present — `[]` means no claims yet, not "unavailable") from this collection via a `$unwind`/`$group`/`$toDecimal` aggregation exactly like the bridge deposit/withdrawal stats, combining both claim types into one lifetime total per denom.
- `routes/transactions.ts`'s `GET /transactions` accepts a `type` query param (exact `messageTypes` array-contains match, backed by the `message_types` multikey index in `db/indexes.ts`) and `GET /transactions/message-types` returns every distinct value currently indexed (sorted) — this pair is what powers the type filter dropdown on `apps/web`'s Transactions page; add a new decoded message type to `packages/shared/src/encoding/msg.ts` and it shows up in that dropdown automatically once at least one such tx is indexed, no route change needed.
- `GET /transactions/:hash` also accepts an EVM-format hash (`0x` + 64 hex — what MetaMask/an EVM wallet links to) for a `MsgEthereumTx`, falling back to a `messages.data.hash` lookup (the `evm_tx_hash_sparse` index in `db/indexes.ts`) when the outer Tendermint-hash lookup misses — `decodeMsgEthereumTx` in `packages/shared` always lowercases that inner hash, so the fallback query does too. The response is still keyed by the outer hash either way. `apps/web/src/pages/TransactionDetail.tsx` has a second fallback beyond that: if *neither* lookup finds a wrapper tx at all (e.g. the indexer hasn't caught up to that block yet), it queries `GET /evm/tx/:hash` directly and renders a standalone EVM-only view via the shared `EvmExecutionPanel` component — real EVM data has never depended on this indexer, only the Cosmos-side wrapper does, so there's no reason to show a bare "not found" when the chain's own EVM JSON-RPC still knows about it. Don't hardcode "Contract Call" as the label for every `MsgEthereumTx` (this repo did, once) — `getEvmTxKindLabel()` derives it from the actual EVM details (decoded `method`, else "Contract Creation" when `to` is null, else "Contract Call" only when `toIsContract`, else "STEEM Transfer" for a plain native-value send) since a `MsgEthereumTx` is just a wrapper and says nothing on its own about what happened inside it.
- The `ethereum_tx` event's attributes (`ethereumTxHash`, `txHash`, `recipient`, `amount`, `txGasUsed`, `txIndex`) are the one place in `TransactionDetail.tsx`'s compact "Fund Flow & Events" renderer that broke `apps/web/src/utils/helper.ts`'s `parseCoinString()` — a bare hex hash/address (`"0x55ec84cd..."`, or a lowercased Tendermint hash with no `0x`) coincidentally matches its "digit run then letters" Coins.String() regex (e.g. `"0x55ec..."` parses as amount `"0"` + denom `"x55ec..."`), so it rendered as garbage like `"0 X55EC84CD..."` instead of the hash. `parseCoinString()` now bails out first for anything 0x-prefixed or long-all-hex. Separately, this event's `amount` attribute is bare wei with **no** denom suffix (unlike a bank-module event's `"998000000000000000asteem"`-style concatenation) — `parseCoinString()` correctly won't match it, so it's formatted directly as `formatCoinAmount(value, 'asteem')` instead, keyed on `event.type === 'ethereum_tx' && attribute.key === 'amount'`. Also: this event's attribute keys are camelCase, not the snake_case every other Cosmos event uses — `humanizeModuleName()` originally only split on `_`, so these rendered squished ("EthereumTxHash"); it now also splits camelCase boundaries.
- `src/db/schemas/*.schema.ts` — Zod schema + inferred type per Mongo collection: `blocks`, `transactions`, `validators`, `proposals`, `chainParams`, `denomMetadata`, `indexerState`, `bridgeDeposit`, `bridgeWithdrawal`, `ibcDenomTrace`, `liquidityPool`. No dedicated `accounts` collection — "recent accounts" and "account tx history" are served directly off `transactions.senders` (indexed) rather than maintaining a derived collection.
- Env is Zod-validated and fails fast at startup (`src/config/env.ts`) — see `apps/api/.env.example` for the full list. Only `MONGODB_URI` and `RPC_ADDRESS` are required; `EVM_RPC_URL`/`EVM_EXPLORER_API_URL` (EVM tx decoding, token holdings, liquidity pools) and `STEEMBRIDGE_LCD_URL` (bridge deposits/withdrawals, name service) each gate an entire feature area and are simply unavailable when unset — the app must run with just the two required vars. Real secrets go in `apps/api/.env` (gitignored) — never in `.env.example`.

### Chain module reference (the chain SVM Scan indexes, not this repo)

The chain itself lives in a separate repo — [`blazeapps007/SteemVirtualMachine-EVM`](https://github.com/blazeapps007/SteemVirtualMachine-EVM), its `docs/` folder (`GRPC_AND_REST_REFERENCE.md`, `EVM_JSONRPC_REFERENCE.md`, `CLI_REFERENCE.md`) is the authoritative spec for module/RPC behavior when `steembridgeLcd.ts`/`evmRpc.ts` need extending. Useful facts pulled from there:

- **EVM side**: chain ID `8163` (`0x1fe3`), standard `eth`/`net`/`web3`/`txpool`/`debug` JSON-RPC namespaces. Three chain-*custom* precompiled contracts: `SteemBridge` at `0x0000000000000000000000000000000000000900` (wraps the `steembridge` module — `confirmName()`/`bridgeOut()`), `OracleData` at `...0902` (read-only `getPrice(pair)`), and `SBD` (an ERC-20 precompile mirroring native `asbd`) at `...0901`. The chain also activates the 9 *standard* `cosmos/evm` precompiles at their usual addresses (`p256` `...0100`, `bech32` `...0400`, `staking` `...0800`, `distribution` `...0801`, `ics20` `...0802`, `bank` `...0804`, `gov` `...0805`, `slashing` `...0806`, `ics02` `...0807`) — SVM Scan doesn't call any of these (there's no reason to: ABCI/LCD already gives read access to the same module state with far less plumbing than EVM call+ABI-decode, and nothing here needs an EVM-side *write*), but know they exist before assuming a Cosmos-module feature needs a precompile call to reach from this codebase. Native gas token is `asteem`, 18 decimals.
- **`steembridge` module** (`steemvm.steembridge.v1`, queried over LCD in `chain/steembridgeLcd.ts` since no generated proto exists) — `params`, `deposit`/`pending_deposits`, `withdrawal`/`requested_withdrawals`, and the `name*` endpoints are wired up; still-unused read endpoints if extending further: `bridge_statistics` (see below for why this one specifically isn't called anymore), `deposit/{id}`, `deposit_by_txid/{txid}/{op_index}`, `minted_deposits`, `withdrawal/{id}`, `processed_withdrawals`, `name_registration_by_txid/{txid}/{op_index}`, `awaiting_name_registrations_by_destination/{address}`, `validator_identity/{validator_address}` — reach for these instead of re-deriving equivalent data client-side. The gateway account is a hardcoded chain constant (`svm.bank`) — `Params.gateway_account` (surfaced read-only via `GET /api/params`'s `bridge.gatewayAccount`) is display-only, not something to branch logic on. A withdrawal moves `REQUESTED` → `PROCESSED` once a validator submits `MsgAttestWithdrawalPayout` confirming the Steem-side payout (`steemPayoutTxid`/`processedAtHeight` on `BridgeWithdrawal`); it moves `REQUESTED` → `REFUNDED` instead if it sits unconfirmed past `withdrawalTimeoutBlocks` (`refundedAtHeight`) — don't assume every withdrawal resolves through the payout path. Bridging out withholds a protocol fee (`feeMillisteem`, sent to the `bridge_reward` module account) separate from the principal (sent to `steemblackhole`, the module account with mint+burn permissions that also mints deposits) — see the `MsgBridgeOut` tx's own events for that split, it isn't summarized anywhere as a single field. Deposits and withdrawals both carry an `asset` field — `BRIDGE_ASSET_STEEM` (mints/burns `asteem`) and `BRIDGE_ASSET_SBD` (mints/burns `asbd`) have both been observed live, both at 18 decimals under the same `amountMillisteem`/`amountAsteem` numeric convention, just a different denom suffix in the mint/burn events. Never hardcode "STEEM" as a display unit anywhere a deposit/withdrawal amount is shown — use `bridgeAssetSymbol(asset)` (`apps/web/src/utils/helper.ts`) instead, which just strips the `BRIDGE_ASSET_` prefix; the bridge pages got this wrong once already (every amount hardcoded " STEEM" regardless of `asset`, so an SBD deposit displayed with the wrong unit) before being fixed to read the real per-row `asset`.
- **Bridge totals are computed from our own Mongo, not the chain's `bridge_statistics` LCD endpoint** (that function, `fetchBridgeStatistics`, was deleted along with its two call sites once this changed) — because that endpoint only ever tracked STEEM, so it silently excluded SBD volume with no way to tell from the response alone. `GET /bridge-deposits/stats`'s `mintedByAsset` and `GET /bridge-withdrawals/stats`'s `withdrawnByAsset` are instead a `$group`/`$sum`-over-`$toDecimal` Mongo aggregation on `bridgeDeposits`/`bridgeWithdrawals`, grouped by `asset`, returned as `BridgeAssetTotal[]` (`{ asset, amountMillisteem }`) — `$toDecimal` matters here, summing the string-encoded amounts as plain numbers would lose precision. `mintedByAsset` only counts `DEPOSIT_STATUS_MINTED` docs; `withdrawnByAsset` is intentionally *not* status-filtered (REQUESTED/PROCESSED/REFUNDED all count), since the burn already happened by the time a withdrawal is indexed at all. `GET /bridge-deposits/stats` also returns `countByAsset` (`BridgeAssetCount[]`, `{ asset, count }`) — a plain `$group`/`$sum: 1` count of deposits per asset regardless of status, same idea as `mintedByAsset` but counting rows instead of summing amounts. Both frontend bridge pages render one stat card per entry in these arrays rather than assuming exactly STEEM+SBD, so a third bridged asset would just show up as another card with no code change. **Name registrations (`MsgSubmitNameRegistration`) also mint** — `NameRegistration.amountMillisteem` is minted to `derivedDestination` via `steemblackhole` on confirmation, the exact same mint mechanism as a bridge deposit (verified live: a `MsgSubmitNameRegistration` tx's events include `coinbase`/`transfer` from `steemblackhole` identical in shape to a deposit's). It is tracked entirely separately from bridge deposits though — a different LCD list (`name_registration*`, not `deposit`), a different Mongo collection, a different frontend page (SVMNS, not Bridge) — so a name-registration mint will never appear as a row in the Bridge Deposits list, nor count toward `mintedByAsset`, since that's now purely a `bridgeDeposits` aggregation; that's by module design, not a missed-indexing bug, and the Bridge Deposits page carries an inline note saying so. Don't call the registration's minted amount a "registration fee" anywhere in the UI — nothing is withheld, the full amount is minted to the destination.
- **`oracledata` module** (`steemvm.oracle.data.v1`, queried over LCD in `chain/oracleLcd.ts`) — commit-reveal validator voting that produces a power-weighted-median rate per whitelisted pair (`STEEM/USD_External`, `SBD/USD_External`, `STEEM/SBD_Internal`, `Price_Feed`). `params` and `exchange_rates` are wired up (`GET /api/params`'s `oracle` field, `GET /api/oracle/exchange-rates`); `exchange_rate/{pair}` (single-pair), `aggregate_prevote/{validator}`, and `aggregate_vote/{validator}` (in-flight commit-reveal state, not the finalized rate) are not.

### `apps/web` — frontend

- `src/lib/apiClient.ts` is the single fetch choke point (`apiClient.get<T>('/path')`, base URL from `config.apiBaseUrl` / `VITE_API_BASE_URL`) — the RPC-layer equivalent of what `src/rpc/*` used to be in the original fork.
- `src/hooks/useApiHealth.ts` polls `GET /api/health`; `App.tsx` gates the route tree on it (API unreachable → a message screen, not a "connect" form — there's nothing to configure client-side).
- Data-fetching hooks (`useHomeData`, `useAccountData`, `useProposalData`, `useIBCTransfers`, `useBridgeDeposits`, `useBridgeWithdrawals`, `useNameService`, `useOracleData`) are thin `useQuery` wrappers around REST endpoints, with `refetchInterval` used for "live" feel on list/dashboard views — there is no WebSocket/SSE push from the backend, polling is the deliberate simple choice.
- Detail pages (`BlockDetail`, `TransactionDetail`, `ValidatorDetail`, `ProposalDetail`, `AccountDetail`, `BridgeDepositDetail`, `BridgeWithdrawalDetail`, `SVMNSRegistrationDetail`) fetch by route param via one-shot `useQuery`, no polling.
- EVM-side and bridge/name-service ("SVMNS") features degrade gracefully when their backing env vars are unset on the API — routes return empty data or 404/503 rather than erroring, so the frontend should treat those as legitimately-empty states, not failures.
- `components/ProposalDetail/VotingResults.tsx`'s `finalTallyResult` counts (`yesCount`/`noCount`/`abstainCount`/`noWithVetoCount`) are bonded voting *power* in atto units (same base-unit convention as any Coin amount, e.g. `"104792000000000000000000"` = 104,792 STEEM of power), not a literal ballot count — this component used to run them through plain `Number()` and label the result "votes," which both silently lost precision past `Number.MAX_SAFE_INTEGER` and showed a meaningless huge integer. It now converts through the standard `getConvertedAmount(raw, 'asteem')` + `formatAmount()` pipeline like every other atto amount, labeled "STEEM" instead of "votes."
- `components/ProposalDetail/ProposalVotesList.tsx` renders the per-voter breakdown from `GET /proposals/:id/votes` (see the `routes/proposals.ts` bullet above for the live-proxy/pruning caveat) — its empty-state message is worded differently depending on `proposal.status` (`CONCLUDED_STATUSES`), since an empty result means something different for an active vs. concluded proposal.
- `components/ValidatorIcon.tsx` shows a validator's Steem avatar (`https://steemitimages.com/u/{moniker}/avatar/small`), falling back to Keybase (`identity`, the standard Cosmos validator field) and finally to an initial-letter placeholder. This relies on a chain-specific fact verified live, not assumed: validator monikers on this chain *are* Steem account names (e.g. `"blaze.apps"`/`"xpilar.witness"` are real Steem accounts — their `description.details` even embeds that account's STM-prefixed owner/active/posting keys), so `moniker` doubles as the steemitimages lookup key with no separate field needed; `identity` has been empty on every validator observed so far, hence trying Steem first. steemitimages responds `200` with a JSON error body (not an image) for an unknown account rather than `404`ing — the browser still can't decode that as an image and fires the `<img>`'s `onError` correctly, which is what the Keybase fallback is gated on; don't "fix" that 200 into a success case if this component is ever touched again.

### Extending message-type decoding

`packages/shared/src/encoding/msg.ts` is a `typeUrl → decoder` map (`TYPE` object + `switch` in `decodeMsg`) — this is **the** extension point for supporting more Cosmos SDK message types, including the chain's custom `steembridge` module messages (`MsgAttestDeposit`, `MsgBridgeOut`, `MsgSubmitNameRegistration`, `MsgConfirmName`, `MsgAttestWithdrawalPayout`) and `oracledata` module messages (`MsgAggregateExchangeRateVote`/`MsgAggregateExchangeRatePrevote`, the reveal/commit halves of price-feed voting — `exchangeRates` on the Vote decodes to a parsed `{pair, rate}[]`, not the raw comma-separated string, since the CSV format is simple and was verified against a real tx), all hand-decoded field-by-field since no generated proto package exists for either module. Every one of these `TYPE` entries must match the chain's *real* on-chain type name exactly — a wrong-but-plausible-looking name (this repo shipped with the deposit-attestation message registered as `MsgSubmitSteemDeposit` for a while; the real name is `MsgAttestDeposit`) fails silently: it doesn't error, it just falls through to the generic decoder below on every matching tx, forever, with no signal that anything's wrong. If a tx's decoded messages show generic `field_1`/`field_2` keys where you'd expect real field names, check the `typeUrl` against a live query first before assuming the field layout needs re-deriving — the type name is usually the actual bug. Field layouts for these custom messages are verified by hand-walking a real tx's raw protobuf bytes (not guessed from the LCD's REST field names, which use different field numbering) — `MsgAttestWithdrawalPayout` specifically was verified by diffing two real txs for different withdrawal ids, since proto3 omits a zero-valued field on the wire (same trick used elsewhere in this file for `op_index`). An unrecognized `typeUrl` falls through to `decodeUnknownMessage()`, a best-effort generic protobuf-field decoder (numbered fields, printable strings/addresses surfaced where possible) rather than throwing or returning nothing — both in the indexer and anywhere else `decodeMsg` is called. When adding a new message type, add it here once — both `apps/api` (indexing) and `apps/web` (if it ever needs client-side decoding again) pick it up automatically since both import from `@dexplorer/shared`. This registry is also what governance proposal messages decode through (`indexer/proposalRefresh.ts` calls the same `decodeMsg`) — a gap here shows up as `field_1`/`field_2` on the Proposal Detail page's Messages card too, not just on transactions.

`MsgVote`/`MsgVoteWeighted` (`/cosmos.gov.v1`) decode fine via generated cosmjs-types (no gap there), but both left `field.key === 'proposalId'`/`'option'` rendering as a bare number with no link — `TransactionDetail.tsx` now special-cases these two typeUrls (`VOTE_MESSAGE_TYPES`) to link `proposalId` to `/proposals/:id` and label `option`/`options[]` via `voteOptionList` (`packages/shared/src/utils/constant.ts`, keyed by the numeric VoteOption wire value — confirmed live that even a plain `MsgVote` carries this as a *string* on `cosmos/gov/v1/proposals/{id}/votes`' LCD JSON but as a raw *number* on the ABCI-decoded message and on the `proposal_vote` event's embedded JSON, so the two lookups key differently: `voteOptionList[].id` (number) for the decoded message, `voteOptionList[].option` (string) for LCD JSON like `ProposalVotesList.tsx` consumes). The tx's `proposal_vote` event (distinct from the decoded message — carries a JSON array string even for a non-weighted vote, e.g. `option: [{"option":1,"weight":"1.0..."}]`) gets the same proposalId-link/option-label treatment in the compact events renderer, keyed on `event.type === 'proposal_vote'` rather than the message typeUrl.

Standard (non-custom-module) Cosmos SDK message types can be missing a decoder here too if `cosmjs-types` doesn't happen to ship generated types for that specific module — `MsgUpdateParams` from `cosmos.evm.feemarket.v1` (the EVM base-fee/min-gas-price governance parameter, e.g. proposal #1 on this chain) is hand-decoded the same way as the custom steembridge/oracledata messages, verified against the real public proto (`github.com/cosmos/evm`) *and* cross-checked byte-for-byte against a real proposal's LCD JSON — worth knowing since it's easy to assume "well-known Cosmos module = already covered by cosmjs-types," which isn't always true for newer/less-common modules. Its nested `Params` sub-message uses `LegacyDec` fields (base_fee/min_gas_price/min_gas_multiplier) — `decodeLegacyDecString()` (exported from `@dexplorer/shared`, alongside the other denom-conversion utils in `utils/cosmos.ts`) converts the raw wire encoding (the internal value-times-10^18 big integer, as an ASCII digit string) into the same human-decimal string form ABCI-decoded Dec fields already use elsewhere (e.g. `"100000000000000.000000000000000000"`), reusable for any future hand-decoded LegacyDec field. Its sibling `cosmos.evm.vm.v1.MsgUpdateParams` (the EVM module's own params — `evm_denom`, extra EIPs, create/call access control, `active_static_precompiles`; first seen in proposal #3, which drops the staking precompile `…0800` from that list) is hand-decoded the same way as `MsgUpdateEvmParams`, field numbers from `cosmos/evm` **v0.7.2** (the version the chain's `go.mod` pins — check that before trusting a newer proto, since fields get reserved/renumbered between releases) and verified against proposal #3's raw submission-tx bytes vs its LCD JSON. `indexer/validatorRefresh.ts` is the other real caller: a validator's `delegatorShares` (`cosmjs-types`-decoded, not hand-decoded, but still a raw-wire `Dec`) is *also* denominated in the bond token's atto units, so it needs `decodeLegacyDecString()` applied before storage — skip it and the value silently comes out 10^18x too large everywhere it's displayed (this shipped once: Validator Detail's "Delegator Shares" showed e.g. `"800000000000.00B STEEM"` for what should have read `"800 STEEM"`). `tokens` and `minSelfDelegation` on the same struct are plain `Int`s, not `Dec`s, so they don't need this — only fields whose proto type is actually `Dec`/`LegacyDec` do.

A fourth gap shape, distinct from the three above: `cosmos.mint.v1beta1.MsgUpdateParams` (a proposal changing the inflation module's params, e.g. proposal #2 on this chain, zeroing out inflation) — `cosmjs-types@0.9.0` *does* generate a full decoder for this one (unlike feemarket's), but its embedded `Params` type is missing `max_supply`, a newer SDK field this chain's real proposal data actually populates. The generated decoder doesn't error on the unknown field, it just silently drops it, which would permanently lose that value rather than showing `field_7`/garbage — a quieter failure mode than the others documented here, worth remembering: "cosmjs-types has *a* decoder for this type" isn't the same guarantee as "cosmjs-types decodes *every field* of this type." `decodeMsgUpdateMintParams()`/`decodeMintParams()` hand-decode it instead (field 7, wire type 2, an `sdk.Int` string — verified by hand-walking a real proposal's raw tx bytes, cross-checked against its LCD JSON), registered as `MsgUpdateMintParams` in `TYPE` (its real on-chain typeUrl is also literally `.../MsgUpdateParams`, same name collision as feemarket's, hence the disambiguating `TYPE` key).

A third gap shape: `cosmjs-types` *does* generate a decoder for the outer message but leaves a polymorphic `google.protobuf.Any` field undecoded — `MsgGrantAllowance` (`cosmos.feegrant.v1beta1`) decodes `granter`/`grantee` fine via the generated type, but its `allowance` field is an `Any` (one of `BasicAllowance`/`PeriodicAllowance`/`AllowedMsgAllowance`) that arrives as raw `{typeUrl, value: Uint8Array}` unless decoded further. `decodeMsgGrantAllowance()` (`packages/shared/src/encoding/msg.ts`) decodes that nested `Any` against whichever concrete allowance type its `typeUrl` names, recursing one level for `AllowedMsgAllowance` (which itself wraps another `Any`) — verified live against tx `8DEB941F...B034DC`, a `BasicAllowance` with an empty `spend_limit` and no `expiration` (i.e. an unlimited allowance). `MsgRevokeAllowance` has no `Any` field and decodes fully via the generated type with no extra work.

`apps/api/src/routes/transactions.ts`'s `GET /transactions/:hash` also resolves every bech32 address appearing in a tx's raw `events` to its Cosmos SDK module account name (`fee_collector`, `bridge_reward`, `steemblackhole`, ...) via `chain/moduleAccounts.ts` (the standard `/cosmos/auth/v1beta1/module_accounts` LCD endpoint — module account addresses are derived from the module name, so this is safe to cache for a long time, currently 1h) — returned as `moduleAccounts` on `TransactionDetailResponse`, consumed by `TransactionDetail.tsx`'s Events section to label things like "steemblackhole receives 998 asteem" instead of showing a bare address with no context. Gated on `STEEMBRIDGE_LCD_URL` like the rest of the bridge features, since it's the same LCD.

### Theming (apps/web)

`src/theme/ThemeProvider.tsx` is a React context (light/dark/system, persisted to `localStorage`) that writes CSS custom properties (`--color-*`) onto `document.documentElement` from the palette in `src/theme/colors.ts`. Components read theme via `useTheme()`.

### Path aliasing

`@/*` maps to `apps/web/src/*` (declared in `apps/web/tsconfig.app.json`, resolved via the `vite-tsconfig-paths` plugin) — only within `apps/web`. `apps/api` and `packages/shared` use plain relative imports; cross-workspace imports go through the `@dexplorer/shared` / `@dexplorer/api` / `@dexplorer/web` package names (pnpm workspace symlinks), never `@/...` across an app boundary.

### Single-container deployment

The `Dockerfile` builds `apps/web` and runs `apps/api` as one process serving both the REST API and the built frontend behind one port — `apps/api/src/server.ts` registers `@fastify/static` against `STATIC_DIR` (set only in the container, e.g. `apps/web/dist`) and falls back to `index.html` for non-`/api` routes so client-side routing survives a full page load. `docker-compose.yml` + `deploy/nginx/` (reference reverse-proxy config) drive this; local dev leaves `STATIC_DIR` unset and runs Vite + Fastify as two separate dev servers instead.

## Coding Standards

### Core Principles

- **Immutability**: NEVER mutate objects. Return new state objects.
- **Type Safety**: strict `no-any` policy. Define proper interfaces. Prefer a typed cast (`as SpecificType`) over `any` when a library's inferred type is wrong or too loose.
- **Functional**: Use functional components and hooks.
- **Clean Code**: Functions < 50 lines, Files < 400 lines. Group by feature.

### Architecture & Pattern

- **Component Structure**: Group by feature (`components/AccountDetail`, `components/ProposalDetail`, `components/Home`, etc.). High cohesion.
- **Error Handling**: `try/catch` all async ops. Throw user-friendly errors.
- **New chain data needs**: add a route in `apps/api/src/routes/`, a type in `packages/shared/src/types/api.ts`, then a `useQuery` in the relevant `apps/web` hook — don't add a new direct chain call from the frontend.

### Workflow & Requirements

- **Git**: Conventional Commits (`feat:`, `fix:`, `refactor:`, `docs:`, `test:`, `chore:`).
- **TDD**: Write tests first (Red -> Green -> Refactor).
- **Testing Goal**: 80% coverage (Unit, Integration, E2E). `apps/api` route tests use `mongodb-memory-server` (see `apps/api/test/routes/`) — no live chain/Mongo needed to run them.
- **Verification**: ALWAYS run `pnpm lint` and `pnpm check` after every task completion to ensure code quality and type safety.
- **Security**: No hardcoded secrets — real credentials only in gitignored `.env` files, never `.env.example`.
- **API docs stay in sync**: `docs/openapi.yaml` is the source of truth for the public REST API reference (built with Redoc, published to GitHub Pages by `.github/workflows/docs.yml`). Any change that adds, removes, or changes the shape of an API route (`apps/api/src/routes/*.ts`), a shared response type (`packages/shared/src/types/api.ts`), or a MongoDB schema field that flows into a response — update the matching path/schema in `docs/openapi.yaml` in the same change, not as a follow-up. Use a real example response (fetched live, not fabricated) the same way the rest of the spec does.

## Known Issues (Fix Priority)

- **High**: Large components (`AccountDetail`, `ProposalDetail`, `Home`).
- **Medium**: `apps/web` polling intervals are per-hook constants rather than centrally tuned; revisit if API load becomes a concern.
- **Medium**: No push (WebSocket/SSE) channel from `apps/api` to the frontend yet — "live" views are polling-based. Noted as a deliberate Phase 1 scope boundary, not an oversight.
